# 06 · 性能分析：压测、找瓶颈、验证修复

对应文件：`tools/loadtest/mixed.js`（k6 压测脚本）、[benchmark.md](../benchmark.md)（压测结果和方法）、[engineering-log.md](../engineering-log.md)（排查过程）。

这一篇讲的不是某个技术点，而是**方法**。面试官最想知道的是：你遇到性能问题时怎么思考。

## 1. 压测怎么做才可信

**开放模型 vs 封闭模型**

- 封闭模型：N 个虚拟用户，每个等上一个请求返回了再发下一个。服务一变慢，发请求的速度也跟着降，排队延迟就被掩盖了。这叫 **coordinated omission**（协同遗漏）。
- 开放模型：不管服务快慢，每秒固定发 R 个请求（k6 的 `constant-arrival-rate`）。这更接近真实世界，用户不会因为你的服务慢就少来。

**看分位数，不看平均值**

- 平均值会被大量快请求稀释。P95、P99 才反映"最倒霉的那批用户"的体验。
- Prometheus 里用直方图记录延迟，查询时再用 `histogram_quantile` 算分位数。

**阶梯加压找拐点**

- 每秒 250、500、750、1000 个请求，逐级往上加，找到延迟突然飙升或者开始出错的那一档，那就是当前的容量上限。

**确认测的是你的系统**

- 我们踩过的坑：经过 Docker 的端口转发代理去压测，测到的是代理的瓶颈，而不是服务。
- 判断方法：对比客户端看到的失败数和服务端日志里的失败数。差距很大，说明问题在中间链路上。

**写清楚测试环境**

- 硬件（4 vCPU、16GB 内存）、数据量（10 万篇帖子）、流量比例、压测工具和被测系统是否在同一台机器上。
- 不写这些，数字就没有意义。

## 2. 找瓶颈的套路

我们在 Feed 拖垮搜索这件事上，完整走了一遍下面的流程：

```
现象 → 看错误码/日志 → 看资源 (CPU/线程池/连接池) → 提出假设
     → 做对照实验验证假设 → 定位到具体环节 → 修复 → 用同样的实验验证效果
```

关键点：

1. **先看错误是什么**：日志显示 503，对应 ES 返回的 429，再查 `_cat/thread_pool` 看到 5 万次拒绝，证据链完整。
2. **假设要用实验验证**：第一个假设是"Feed 请求并发太多"。我们加了 bulkhead 限流，结果发现没用，说明假设错了。这一步很重要，否则会在错误的方向上越走越远。
3. **对照实验**：把 Feed 流量比例设为 0，其他条件全部不变，系统就不崩了。这样就确定了 Feed 是罪魁祸首。
4. **测成本，不只测延迟**：ES 自己报告查询只花了 5ms，但实际吃掉约 50ms 的 CPU，因为 kNN 会把查询拆到多个核上并行执行。只看延迟会被误导。
5. **分阶段计时**：把一次请求拆成 7 个阶段分别计时，发现大部分时间花在传输和解析 embedding 上，而不是查询本身。
6. **先算性价比，再决定优化什么**：最贵的 MLT 查询只贡献了 1% 的结果，于是关掉它。关掉之后，用 top-20 重合度 100% 证明推荐质量没有下降。

## 3. 几个常用的解决模式

| 模式 | 解决什么 | 本项目 |
|---|---|---|
| **批量化（batching）** | 往返次数太多 | reindex 改用 `_bulk`，快了 28 倍；列表接口的点赞信息用一次查询批量取 |
| **只取需要的数据** | 序列化和传输成本 | 召回阶段只取 id、作者、时间，最后只补全前 20 篇的正文 |
| **舱壁隔离（bulkhead）** | 一个昂贵的功能拖垮整个系统 | Feed 最多同时 2 个请求，超出的快速返回 503，前端回退到 Latest |
| **熔断/暂停（circuit breaker）** | 依赖宕机时还在白白重试 | outbox worker 在 ES 宕机时整体暂停 |
| **缓存 / 预计算** | 重复计算 | 列为下一步：缓存口味向量、预计算 Feed |
| **离线优化数据结构** | 查询时的结构性开销 | 重建索引后 force merge 成 1 个段 |

## 4. 面试时怎么讲这段经历（STAR 结构）

- **S（情境）**：加入个性化 Feed 后做混合负载压测，到每秒 1000 个请求时系统崩了，搜索 P50 达到 4.5 秒。
- **T（任务）**：找到根因，让 Feed 的问题不再拖垮核心的搜索功能。
- **A（行动）**：
  1. 从错误码一路追到 ES 线程池，发现被拒绝了 5 万次；
  2. 第一个假设（并发太多）被实验否定；
  3. 单独压测 Feed，发现每次请求约耗 50ms CPU；
  4. 分阶段计时、按召回源统计贡献，做了三项优化：精简传输字段、关掉低价值的 MLT 查询、force merge。
- **R（结果）**：用具体数字说明各项改进（见 benchmark.md）。同时诚实说明剩下的限制，以及下一步的架构方案。
