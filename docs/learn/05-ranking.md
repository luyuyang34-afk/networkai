# 05 · 推荐系统：两阶段召回 + 排序

对应代码：`internal/feed/feed.go`（在线服务）、`internal/embed/lsa.go`（embedding）、`tools/ranking/train_eval.py`（离线训练和评估）。设计文档：[ranking.md](../ranking.md)，评估报告：[ranking-eval.md](../ranking-eval.md)。

## 为什么要分两阶段

候选池里有几十万篇帖子，不可能每篇都用复杂模型打分。所以拆成两步：

| 阶段 | 目标 | 方法 | 处理量 |
|---|---|---|---|
| 召回（retrieval） | **找全**：别漏掉用户可能喜欢的 | 便宜、粗糙：向量近邻、关键词、最新 | 几十万 → 几百 |
| 排序（ranking） | **排准**：最好的排在最前 | 贵、精细：多特征模型打分 | 几百 → 前 20 |

这和 AI Document Q&A 项目里的"粗召回 + cross-encoder 精排"是同一个思想。面试时把两个项目连起来讲，会显得很有体系。

## 召回的三个来源

1. **语义（semantic）**：用户最近点赞帖子的 embedding 取平均，得到"口味向量"，然后在 ES 里做 kNN，找最相近的帖子。
2. **词法（lexical）**：ES 的 `more_like_this`，找和点过赞的帖子用词相似的帖子。（**默认已关闭**：实测它在最终结果里只独家贡献了 1%，却是最贵的查询。这本身就是一个很好的面试故事。）
3. **最新（fresh）**：最新的帖子。没有点赞历史的新用户（**冷启动**）只能靠这一路；它也给新话题曝光的机会（exploration）。

### kNN 和 HNSW

- 精确 kNN 需要拿查询向量和每一篇文档算距离，太慢。
- **HNSW**（Hierarchical Navigable Small World）是一种多层图结构，可以在图上"跳跃"着找近邻。它是近似的，但非常快。
- `num_candidates` 控制搜索的广度：越大越准，也越慢。
- **一个坑**：每个 Lucene 段（segment）各有一张 HNSW 图，查询要在每张图上都搜一遍。批量导入后有 28 个段，force merge 成 1 个段之后，ES 的 CPU 消耗降了 30%。

## 排序：逻辑回归

特征（定义见 `feed.Features`，必须和训练脚本完全一致）：

| 特征 | 含义 |
|---|---|
| cosine | 口味向量和帖子 embedding 的相似度 |
| freshness | exp(−小时数/24)，越新越接近 1 |
| log_likes | log(1+点赞数)，衡量受欢迎程度 |
| author_affinity | 用户以前给这个作者点过多少赞 |

模型是 `score = w·标准化(特征) + b`。为什么用逻辑回归？
- 可解释：权重直接说明了每个特征的作用；
- 训练快；
- 线上打分就是一次点乘；
- 是业界常见的 baseline。

下一步可以换成梯度提升树（GBDT），或者 learning-to-rank 模型（LambdaMART）。

排完序还有一步**多样性**处理：每个作者最多 2 条。没有这一步时，一个作者连发的近似帖子把整个 Feed 都占满了（真实踩过的坑）。

## 离线评估：怎样才算"不作弊"

1. **按时间切分**：前 25 天训练，后 5 天测试。不能随机切分，否则会用"未来"的数据去预测"过去"。
2. **特征只能用过去的数据**：某一天的曝光，它的特征只能用那天之前的点赞来算（`build_examples` 里是逐天累加的）。这叫**防止数据泄漏**（leakage）。
3. **同一批候选**：每种方法都对同一组曝光排序，只比较排序的好坏。
4. **基线**：按时间倒序（就是"最新"Feed）。报告相对基线的提升。

### nDCG@10

- DCG = Σ 相关性 / log₂(位置+1)：相关的结果排得越靠前，分越高。
- 除以理想排序的 DCG，归一化到 0 到 1 之间。
- 只看前 10 个位置，因为用户基本只看前面。

### 消融实验（ablation）

每次去掉一个特征重新训练，看指标掉多少，从而知道哪个特征真正有用。我们的结果：
- 去掉 freshness 掉 15.6%，去掉 cosine 掉 12.2%，这两个最重要；
- 去掉 author_affinity 几乎没变化（合成数据里没有模拟"关注作者"这种行为）。

### 天花板（oracle）

用数据生成器的隐藏变量（真实兴趣、真实质量）直接排序，得到理论上的最好成绩 0.52。我们的模型从 0.36 提升到 0.41，填补了 31% 的差距。这样说比只说"+14%"更诚实，也更有信息量。

## 合成数据：必须能讲清楚

被问到"数据从哪来"，要主动说明：
- 真实数据集在开发环境里下载不了；
- 写了一个有结构的生成器：话题、兴趣、质量、新鲜度衰减；
- 模型**只看可观测的数据**，看不到生成器的隐藏变量；
- 所以评估能证明**流程正确、模型能学到信号**，但**不能代表真实用户上的提升**；
- 换成真实数据集只需要提供同样格式的三个 CSV。

## 线上和离线一致性（training-serving skew）

- 训练用 Python，服务用 Go，两边的特征和 embedding 计算必须完全一致。
- `internal/embed/lsa_test.go` 用 Python 导出的向量来对比 Go 的计算结果（误差 < 1e-4）。故意改坏 TF 公式，这个测试就会失败。

## 自测

1. 为什么不能随机切分训练集和测试集？
2. 新用户没有点赞历史，Feed 怎么出结果？
3. 如果离线 nDCG 涨了，上线以后点赞率反而降了，可能是什么原因？（提示：位置偏差、曝光偏差、反馈循环、离线指标和业务目标不一致）
4. kNN 召回 k=200 改成 k=100，怎么证明推荐质量没有变差？（我们的做法：top-20 结果的重合度达到 100%）
