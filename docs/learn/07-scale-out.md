# 07 · 扩展到大规模：每个问题是什么、怎么修、怎么证明

前六篇讲的是"一台机器上把事情做对"。这一篇讲用户变多以后，哪些东西会**以特定的方式坏掉**。每一节都按同样的顺序讲：

1. 一句话说清楚问题；
2. 打个生活里的比方；
3. 我们怎么修的；
4. 实验数据；
5. 面试官会怎么追问。

先记住一个总原则：**规模问题几乎都不是"流量大"这么笼统，而是某个具体的点被打爆了**。比如：
- 一个大 V；
- 一篇爆款帖子；
- 一个数据库主库；
- 一条跨洋网络。

---

## 1. 大 V 发帖：扩散（fan-out）

**问题**：每个用户有一条"关注的人发的帖子"时间线。最直接的做法是有人发帖时，把帖子 id 塞进每个粉丝的时间线（"推"）。大 V 有 20 万粉丝，发一条就是 20 万次写入。

**比方**：小区物业给每户塞传单，100 户很快。如果是 20 万户，后面排队要发的通知全部被堵住。

**修法**：混合模式。
- 普通人发帖照样推。
- 粉丝超过 1 万的人不推，粉丝打开时间线时再去拉这些人的最新帖子，合并进来（"拉"）。
- 代码：`internal/timeline/timeline.go`。

**数据**：20 万粉丝的大 V 发帖后，普通人的帖子要排队 **1.28 秒 → 14 毫秒**。

**追问**：
- 阈值为什么是 1 万？是在推的写入成本和拉的读取成本之间取平衡，应该按实测调。
- Redis 挂了怎么办？时间线只是缓存，可以从 PostgreSQL 重建。
- 不活跃用户呢？他们的时间线 7 天过期，发帖时也不再推给他们。

## 2. 一个任务拖慢所有任务：CDC + Kafka

**问题**：原来一个 worker 依次做所有事：写搜索索引、推时间线。Redis 一挂，推时间线卡住，搜索索引也跟着停了。

**比方**：一个收银台既收钱又包装，包装纸用完了，收银也停了。正确的做法是每件事各开一个窗口。

**修法**：
- **CDC**（Change Data Capture，变更数据捕获）：直接读 PostgreSQL 的提交日志（WAL），把每次提交发到 Kafka。
- 每种下游任务是一个独立的**消费组**，有自己的进度（offset）：搜索、时间线、统计、缓存失效。
- 一个组卡住只影响它自己，修好后从自己的进度继续。
- 代码：`internal/cdc/`。

**数据**：Redis 挂掉时，发帖到能搜到：**超过 60 秒 → 0.73 秒**。

**追问**：
- 消息会重复吗？会，至少一次投递（at-least-once），所以每个消费者都必须幂等，见第 02 篇。
- 复制槽有什么风险？relay 停了以后 WAL 会一直堆积，最后撑爆磁盘。所以有一条告警专门盯着它。
- 新加一个消费组，能拿到历史数据吗？可以从 topic 开头读（`post-stats` 就是这样）。

## 3. 读副本延迟：自己刚发的帖子看不见

**问题**：读请求分给副本（replica）可以减轻主库压力。但副本同步有延迟，用户发完帖子马上刷新，可能落到还没同步的副本上，帖子就"消失"了。

**比方**：你刚往银行存了钱，马上去另一个网点查余额，那边的账本还没更新。

**修法**：一致性 token。
- 写完以后，把主库当前的日志位置（LSN）返回给客户端。
- 客户端下次读时带上这个 token。
- 副本已经同步到这个位置，才从副本读；没到就读主库。
- 代码：`internal/store/routing.go`。

**数据**：
- 没有人为延迟、同一台机器上：发完立刻读，**31%** 的情况看不到自己的帖子。
- 用 token 以后：**0%**。
- 普通浏览仍然 100% 走副本。

**追问**：
- 为什么不"写后 N 秒都读主库"？N 只能猜：猜小了还会出错，猜大了主库白白承受压力。
- 换一台设备呢？token 存在设备上，所以跨设备不保证。这是一个已经接受的取舍。

## 4. 爆款帖子：热点 key

### 4a. 点赞计数

**问题**：每次点赞都给同一行计数器 +1。数据库的行锁让所有点赞排成一队。

**比方**：一个收银台排了 64 个人。开 16 个收银台，最后把各台的数字加起来就是总数。

**修法**：每篇帖子的计数拆成 16 行，每次随机挑一行 +1，读的时候求和。代码：`bumpLikeCount`。

**数据**：同一篇帖子，**932 → 3,410** 次点赞/秒，计数仍然精确。

### 4b. 缓存击穿（stampede）

**问题**：热门帖子放在缓存里。缓存一过期，几百个请求同时发现"缓存里没有"，同时去查数据库。

**比方**：奶茶店门口的菜单牌被风吹掉了，几百个顾客同时冲进去问店员有什么。

**三层修法**（`internal/postcache`）：
1. **singleflight**：同一个进程里，同一个 key 只让一个请求去查，其他人等它的结果。
2. **租约（lease）**：来自 Facebook memcache 的论文。
   - 跨多台 API 服务器，只有拿到租约的那一个去查库，别人等。
   - 它还解决一个更隐蔽的问题：慢的读者把**旧数据**写回缓存，覆盖掉刚失效的新数据。
3. **XFetch**：快过期时，按概率提前在后台刷新，让大家根本碰不到过期的那一刻。

**数据**（32 个 API 实例）：
- 查库从每秒 **1,192 次降到 4 次**；
- 读到旧数据的比例 **29.5% → 0%**。

**追问**：
- singleflight 不够吗？不够，它只管一个进程。实测查库次数随实例数线性增长：8 个实例每秒 32 次，32 个实例每秒 128 次。
- API 进程刚写完数据、还没来得及删缓存就挂了怎么办？CDC 再删一次，这就是 `cache-invalidation` 消费组。

## 5. 一个数据库装不下：分片和在线迁移

**问题**：所有读写都压在一个主库上，总有上限（写入速度、磁盘、备份时间）。必须把数据拆到多台数据库上，而且用户变多以后还要不停机地继续拆。

**比方**：图书馆一栋楼装不下了，要建第二栋。
- 不能按"书名首字母 mod 楼数"分。加一栋楼，几乎所有书都要换楼。
- 正确的做法是先分成 64 个固定的"书架组"，楼与楼之间整组搬。

**修法**（`internal/shard`）：
- **64 个逻辑分片**：按作者哈希分配。一个作者的帖子都在同一个分片里，查"某人的帖子"只需要访问一台机器。
- **所有权在节点自己手里**：每次写入都在本节点确认"这个分片现在归我吗"。路由器缓存的地图过期了也没关系，会被拒绝，然后重试。
- **在线搬迁**：
  1. 先不加锁地复制几轮；
  2. 最后锁住**这一个分片**几十毫秒，复制剩余的增量；
  3. 交接所有权。

**数据**：2 台 → 4 台，迁移期间持续读写：
- 46,608 次写入，**0 丢失**；
- 每个分片的写入暂停中位数 46 毫秒；
- 对照组"先复制再切换"的朴素做法**丢了 98 条**，而且当时完全没有报错。

**追问**：
- 为什么复制的起点用快照的 xmin？复制那一刻还没提交的事务，提交后会被漏掉。`TestInFlightWriteDuringCopyIsNotSkipped` 专门测这个。
- 跨分片查询怎么办？要访问所有节点（scatter-gather），延迟取决于最慢的那台。所以全局 feed 交给 Elasticsearch。
- 实验里还发现了什么问题？新节点的统计信息是空的，查询计划选错，一次查询从 0.2ms 变成 280ms。修法是迁移后跑 `ANALYZE`。

## 6. 跨区域

### 6a. 延迟

**问题**：欧洲用户访问美国的数据库，一次网络往返 70ms。原来发一条帖子要 6 次往返。

**修法**：把插入帖子、插入 outbox、读回结果合成一条 SQL；拿 token 的查询用 pipeline 跟在后面一起发出去，变成 1 次往返。

**数据**：**429ms → 73ms**。

### 6b. 区域断网：会不会丢数据？

这是整个项目里最"分布式系统"的一个实验，结论要背下来：

| 复制方式 | 两边同时接受写入（脑裂） | 已确认的写入丢失 | 代价 |
|---|---|---|---|
| 异步 | **54,803 条** | 上万条 | 无 |
| 异步 + 租约自我隔离（fencing） | 0 | 隔离前那几秒的写入 | 恢复时间多 3 秒 |
| 同步 | 0 | 0 | 每次提交多 72ms；断网时少数派那边完全不能写 |

**比方**：两个城市各有一个分店。断网后，总部宣布欧洲分店当家。美国分店不知道，还在照常收单。等网络恢复，两本账对不上，这就是脑裂。
- **fencing**：每个分店都要定期续"营业执照"（租约），续不上就自己停业。
- **同步复制**：每笔单都必须两边都记上才算数。最安全，但最慢。

**追问**：
- 这就是 CAP 吗？对。同步模式在断网时选了一致性（C），放弃了少数派一侧的可用性（A）。
- 选哪个？看数据类型：feed 数据用异步 + fencing，钱用同步。

## 7. SLO：怎么知道系统"够健康"

**问题**：告警写成"错误率 > 1%"有两个毛病：一秒钟的抖动也会把人叫醒；而每天 0.2% 的慢性泄漏永远不会触发。

**修法**（`docs/slo.md`）：
- 先定目标，比如每月 99.9% 的请求成功。剩下的 0.1% 是"错误预算"。
- 告警看的是**预算烧得多快**：
  - 1 小时烧掉了 2% 的月预算，立刻打电话叫人；
  - 3 天都在慢慢超支，就开工单。
- 每个条件都同时看一长一短两个窗口：长窗口防误报，短窗口让问题修好后告警尽快消失。
- 告警规则本身有单元测试（promtool），在 CI 里跑。

**追问**：
- 为什么是 99.9% 而不是 99.99%？一次 fenced 故障切换就要 5 秒。一个月 43 分钟的预算容得下几次切换和部署，4 分钟容不下。
- 实验里暴露了什么？feed 在过载时主动拒绝的请求（503）也计入可用性 SLO，几小时就能烧光预算。所以 feed 需要单独的 SLO，或者降级成缓存版本。
