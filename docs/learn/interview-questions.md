# 面试追问清单

每道题按三层组织：第一层是面试官的开场问题，后面是"追问"和"再追问"。

- **练习方式**：合上文档自己讲，讲不出来的那一层就是要补的。
- **答案要点**：基础部分在 01–06 篇，扩展部分在 07 篇、[system-design.md](../system-design.md) 和各个 ADR 里。
- **⭐ 题**：几乎一定会被问到，先练这些。

## A. 开场介绍（用英文练）

**30 秒版本**

> "NetworkAI is a social feed app with a Go backend. PostgreSQL is the source of truth; search, home timelines and caches are derived from it through a transactional outbox and CDC into Kafka, so no dependency outage can lose a write. I then took it through the problems that appear at scale — celebrity fan-out, replica lag, viral-post hot keys, resharding, cross-region failover — and for each one I reproduced the failure, fixed it, and measured the before and after."

**2 分钟版本**：按"架构 → 挑一个最得意的问题讲 STAR → 主动说出局限"的顺序。推荐讲在线扩容分片或缓存租约，这两个最能看出深度。

⭐ **0. 这个项目最难的部分是什么？**
- 追问：你怎么证明你的方案是对的？→ 每个方案都有对照组。比如朴素迁移丢了 98 条，fence 迁移 0 条。
- 再追问：哪个结果出乎你的意料？→ 新节点统计信息过期导致查询变慢；singleflight 在压测里显示 0 条旧数据，但确定性测试证明竞态依然存在。

## B. 数据一致性（基础）

⭐ **1. 为什么不直接写完 PostgreSQL 再写 Elasticsearch？**
- 追问：失败了重试不就行了？→ 进程崩溃时，内存里的重试也跟着丢了。需要一个持久化的"待办"，这就是 outbox。
- 再追问：outbox 和直接发 Kafka 有什么区别？→ 直接发 Kafka 仍然是双写（写数据库 + 写 Kafka），两步之间崩溃就会不一致。

⭐ **2. 你的投递语义是什么？**
- 答：at-least-once（至少一次）。
- 追问：重复消息怎么处理？→ 版本号 + ES 的 external versioning，版本冲突（409）当作成功。
- 再追问：为什么不做 exactly-once？→ 需要分布式事务，成本高。"至少一次 + 幂等"更便宜，效果相同。

**3. 两个 worker 同时处理同一篇帖子的不同事件，会不会写乱？**
- 追问：删除之后迟到的更新，会不会让帖子"复活"？→ 墓碑（tombstone）+ 版本号。
- 再追问：为什么不依赖 ES 自己的删除墓碑？→ `gc_deletes` 默认只保留 60 秒。

## C. 并发与数据库

**4. `FOR UPDATE SKIP LOCKED` 是什么？**
- 追问：去掉 `SKIP LOCKED`，结果还正确吗？→ 正确，但多个 worker 会排队串行。
- 再追问：怎么用测试证明它确实是并行的？

**5. 为什么用 keyset 分页而不是 OFFSET？**
- 追问：两条帖子的 created_at 相同怎么办？→ 用 (created_at, id) 复合排序。
- 再追问：对应的索引怎么建？

**6. 归属检查（"这篇帖子是不是你的"）为什么要 `SELECT ... FOR UPDATE`？**
- 答：先查再改之间有竞态（check-then-act）。

## D. 可靠性

⭐ **7. ES 挂了，你的系统表现如何？**
- 答：发帖和浏览正常；搜索返回 503；outbox 积压；恢复后自动追平。实测 150 秒宕机，0 条写入丢失。
- 追问：`/readyz` 为什么不检查 ES？→ 否则局部故障会变成全局故障。

⭐ **8. 讲一个你遇到的 bug。**
- 可选素材（按推荐顺序）：
  1. 消费者重启后静默跳过消息：21 条只收到 7 条；
  2. 不加 fence 的迁移会静默丢数据；
  3. 长时间宕机会把所有事件打进死信。
- 追问：怎么发现的？→ 写了一个检查每一条已确认写入的测试或实验。
- 再追问：怎么修的？有什么风险？

## G. 规模化（第三轮新增，资深面试官最爱问）

### G1. Feed：推还是拉

⭐ **16. 时间线是推模式还是拉模式？大 V 怎么办？**
- 答：混合模式。普通作者推到粉丝的 Redis 时间线；粉丝超过 1 万的作者，在读的时候再拉。
- 数字：20 万粉丝的大 V 发帖后，普通人的帖子要排队 1.28 秒 → 14 毫秒。
- 追问：阈值 1 万怎么定？→ 在推的写入成本和拉的读取成本之间平衡，应该按实测调。
- 再追问：Redis 挂了或数据被淘汰怎么办？→ 时间线只是缓存，可以从 PostgreSQL 重建；不活跃用户的时间线 7 天过期，发帖时也不再推给他们。

**17. 一个用户关注了 5000 人，读时间线会怎样？**
- 答：拉的部分只针对大 V。大部分内容来自推好的时间线，读取就是一次 ZRANGE。

### G2. CDC 与消息队列

⭐ **18. 为什么从轮询的 worker 换成 CDC + Kafka？**
- 答：一个任务卡住会拖住所有任务。实测 Redis 挂掉时，搜索索引停了 60 秒以上；换成独立消费组后，发帖到能搜到只要 0.73 秒。
- 追问：CDC 是怎么读到变更的？→ PostgreSQL 的逻辑复制槽（logical decoding），读 WAL。
- 再追问：复制槽有什么风险？→ relay 停了以后 WAL 会一直堆积，最后撑爆主库磁盘。所以有一条专门的告警盯着它。

**19. 消费者怎么保证不丢、不重？**
- 答：手动提交 offset，处理完才提交，所以会重复，靠幂等来消化。处理不了的"毒消息"进死信队列（DLQ），同一个分区后面的消息照常处理。
- 追问：遇到过什么坑？→ offset 重置设成 "latest"，消费者重启后静默跳过了 14 条消息；还有每次重启要等 60 秒才能重新加入消费组。
- 再追问：消息顺序怎么保证？→ 按帖子 id 分区，同一篇帖子的事件有序，不同帖子之间不保证。

**20. 新加一个下游任务，能拿到历史数据吗？**
- 答：可以。新消费组从 topic 开头读，`post-stats` 就是这样做的，靠幂等保证重放安全。

### G3. 读副本与一致性

⭐ **21. 读副本有延迟，用户怎么看到自己刚发的帖子？**
- 答：一致性 token。写完返回主库的 WAL 位置（LSN）；读的时候，副本已经同步到这个位置才读副本，否则读主库。
- 数字：发完立刻读，看不到自己帖子的比例 31% → 0%；普通浏览仍然 100% 走副本。
- 追问：为什么不"写后 N 秒都读主库"？→ N 只能猜：猜小了还会出错，猜大了主库白白承受压力。
- 再追问：换一台设备呢？→ token 存在设备上，跨设备不保证。这是一个已经接受的取舍。

**22. 缓存的数据能从副本读来填吗？**
- 答：不能。从落后的副本填缓存，副本追上以后缓存还是错的。实际遇到过：时间线因此错了好几天。

### G4. 热点

⭐ **23. 一篇帖子爆了，系统哪里会先坏？**
- 点赞：所有人改同一行计数器，排队等行锁。改成 16 个分片计数器，932 → 3,410 次/秒。
- 读取：缓存过期的一瞬间，所有请求同时查库（缓存击穿）。
- 编辑以后：慢读者把旧数据写回缓存（stale set）。

⭐ **24. 缓存击穿怎么解决？**
- 答：三层。singleflight（一个进程内合并请求）+ 租约（跨机器只让一个请求去查库，来自 Facebook memcache 论文）+ XFetch（快过期时按概率提前刷新）。
- 数字：32 个实例，查库 1,192 → 4 次/秒；读到旧数据的比例 29.5% → 0%。
- 追问：只用 singleflight 不行吗？→ 它只管一个进程，查库次数随实例数线性增长。
- 再追问：拿租约的那台机器挂了怎么办？→ 租约 2 秒后过期；这期间其他请求直接读数据库，只是不写缓存。

**25. 缓存失效靠什么？API 刚写完数据、还没删缓存就挂了呢？**
- 答：API 写完后删一次，CDC 消费组再删一次。删两次没有副作用。

### G5. 分片

⭐ **26. 数据库装不下了，怎么分片？分片键选什么？**
- 答：按作者哈希到 64 个逻辑分片，用一张目录表映射到物理节点。"某人的帖子"和"按 id 查帖子"都只访问一台机器。
- 追问：为什么不用 `hash % 节点数`？→ 加一台机器，几乎所有数据都要搬。
- 再追问：为什么不按时间分片？→ 所有新写入都落在最新的那个分片上，变成永久的热点。

⭐ **27. 怎么在不停机的情况下扩容（2 台 → 4 台）？**
- 答：
  1. 先不加锁地复制几轮；
  2. 最后只锁住这一个分片，复制剩余的增量（中位数 46 毫秒）；
  3. 源节点先放弃所有权，目标节点再接管。
- 数字：迁移期间 46,608 次写入，0 丢失；朴素的"先复制再切换"丢了 98 条，而且当时没有任何报错。
- 追问：路由器缓存的分片地图过期了怎么办？→ 所有权记在节点自己身上，每次写入都检查。过期的路由器会被拒绝，刷新地图后重试。
- 再追问：增量复制从哪里开始算？→ 从上一轮快照的 xmin 开始。如果用"见过的最大事务号"，会漏掉复制时还没提交的事务。专门写了确定性测试来证明。

**28. 跨分片查询怎么办？**
- 答：要访问所有节点（scatter-gather），延迟取决于最慢的那台：2 台到 4 台，6ms → 11.5ms。所以全局 feed 交给 Elasticsearch 来做。

### G6. 跨区域

⭐ **29. 用户在欧洲，数据库在美国，会怎样？**
- 答：每次网络往返 70ms。发一条帖子原来要往返 6 次（429ms），现在合并成 1 条 SQL，再把拿 token 的查询用 pipeline 一起发，只要 1 次（73ms）。
- 追问：token 为什么不能和写入放在同一条 SQL 里？→ 那样拿到的 LSN 在提交之前，副本可能已经追到这个位置，但还没应用提交记录，读你所写会失效。

⭐ **30. 一个区域断网了，会不会丢数据？**

| 复制方式 | 脑裂写入 | 已确认的写入丢失 | 代价 |
|---|---|---|---|
| 异步 | 54,803 条 | 上万条 | 无 |
| 异步 + 租约自我隔离 | 0 | 隔离生效前那几秒的写入 | 恢复写入多 3 秒 |
| 同步 | 0 | 0 | 每次写入多 72ms；断网时少数派一侧完全不能写 |

- 追问：这和 CAP 有什么关系？→ 同步模式在断网时选了一致性（C），放弃了可用性（A）。
- 再追问：你的系统选哪个？→ 按数据类型：feed 数据用异步 + 隔离，钱相关的数据用同步。

### G7. 可观测性

**31. 你怎么定义"系统健康"？告警怎么设？**
- 答：先定 SLO：可用性 99.9%，读请求 99% 在 250ms 内返回。告警看的是错误预算烧得多快（Google SRE Workbook 的多窗口 burn rate），每个条件同时看一长一短两个窗口。
- 追问：为什么不用"错误率 > 1%"？→ 一秒钟的抖动也会把人叫醒，而每天 0.2% 的慢性泄漏永远不会触发。
- 再追问：告警规则本身怎么测？→ 用 promtool 单元测试，6 个场景，在 CI 里跑。

## H. 推荐 / Feed 排序

**32. "For you" 是怎么生成的？**
- 答：两阶段：先用 kNN 在向量上召回候选，再用学习到的排序模型排序，最后做作者多样性处理。
- 追问：为什么要分两个阶段？

**33. 怎么评估推荐的好坏？**
- 答：离线 nDCG@10，按时间切分训练集和测试集，和按时间倒序的基线对比。
- 追问：怎么防止数据泄漏？
- 再追问：离线指标涨了，线上一定会涨吗？

**34. 你的数据是从哪来的？**
- 答：合成数据。要主动说明它能证明什么（流程正确、模型能学到信号），不能证明什么（真实用户上的效果）。

## I. 性能与压测

⭐ **35. 讲一次排查性能问题的经历。**
- 素材 1：feed 拖垮搜索。搜索 P50 4.4 秒 → 20 毫秒，见 06 篇。
- 素材 2：新分片节点的统计信息过期，一次查询从 0.2ms 变成 280ms。

**36. 你的压测结果可信吗？**
- 答：主动说出局限：单台 4 核机器，压测工具和服务在同一台机器上。

⭐ **37. 如果流量涨 10 倍，先改哪里？**
- 答：先说瓶颈在哪，再说方案。可以直接用 system-design.md 第 7 节"哪个机制在什么规模才需要"那张表来回答。

## J. 工程实践

⭐ **38. 你怎么确认测试真的有效？**
- 答：变异测试：故意删掉关键代码，确认测试会失败。比如删掉 fence 里最后一轮复制，压测发现 1,926 次写入里丢了 14 条。

**39. 偶发失败（flaky）的测试你怎么处理？**
- 答：找出原因，把它写成一个必定触发的测试。比如 relay 在发消息时被关掉会报错：旧代码 15 次随机运行都通过，换成确定性测试后旧代码每次都失败。

⭐ **40. 这个项目最大的不足是什么？**
1. 所有实验都在单机上跑，吞吐量随机器数增长没有测过；
2. 分片子系统还没接进 API；
3. 推荐用的是合成数据；
4. 大模型调用的成本和成功率没有实测。

能主动说出边界是加分项。

| 数字 | 条件 |
|---|---|
| 0 条写入丢失 | ES 宕机 150 秒 |
| 1.28s → 14ms | 20 万粉丝的大 V，普通人帖子的排队时间 |
| >60s → 0.73s | Redis 宕机时，发帖到能搜到 |
| 31% → 0% | 发完立刻读，看不到自己帖子的比例 |
| 932 → 3,410 次/秒 | 同一篇帖子点赞，64 并发 |
| 1,192 → 4 次/秒；29.5% → 0% | 32 个实例读同一篇热门帖子：查库次数；读到旧数据的比例 |
| 0 / 46,608（朴素做法丢 98） | 2 → 4 节点在线迁移 |
| 429 → 73ms | 70ms 往返延迟下发一条帖子 |
| 54,803 → 0 | 区域断网后的脑裂写入（异步 → 加隔离） |
| ~1,200 req/s | 单台 4 核机器的混合负载，压测工具也在同一台机器上 |

## 红线：不要说的话

- **不要说任何没测过的数字。** 引用数字时一定带上前提：单台 4 核机器，多节点和多区域是模拟的。
- **不要说"支持 X 万用户"或"吞吐量线性扩展"。** 没测过。可以说的是"在出现这个问题的规模下，复现并修复了它"。
- **不要说 exactly-once。** 说"至少一次 + 幂等"。
- **不要把 +14% nDCG 说成"点击率提升 14%"。** 它是离线指标，而且是在合成数据上得到的。
- **不要声称大模型调用的成本或成功率。** 没测过。
- **不要说分片已经上线。** 它是单独测过的子系统。
- **被问到不会的**，说"我没做过这个，但我会这样考虑……"，比编造好得多。
