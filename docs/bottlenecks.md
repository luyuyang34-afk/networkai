# 卡点与瓶颈汇总

分两类：**环境卡点**（做不了、需要你出手的事）和**系统瓶颈**（压测和调试中发现的性能/设计问题）。

## A. 环境卡点（需要你决定或提供资源）

| # | 卡点 | 影响 | 现在的处理 | 解决办法 |
|---|---|---|---|---|
| 1 | **拿不到真实交互数据集**（MIND、MovieLens 等托管的域名都被网络策略拦截） | Feed 排序只能在合成数据上评估，**+14% nDCG 不能当成真实用户的提升来讲** | 写了有结构的合成数据生成器，报告里明确标注"合成数据"并说明能证明什么、不能证明什么（`docs/ranking.md`） | 放行一个数据集的域名（例如 MIND 的 `mind201910small.blob.core.windows.net`），或者在本机下载后上传；训练脚本只需要同样格式的三个 CSV 文件 |
| 2 | **HuggingFace 不可访问** | 无法使用预训练的神经网络 embedding 模型 | 用 LSA（TF-IDF + SVD），Go 和 Python 结果一致，有测试保证 | 放行 `huggingface.co`，换成 sentence-transformers；接口不用改，只需重新训练并执行 `reindex -fresh` |
| 3 | **OpenAI API 不可访问，也没有 key** | 写作助手的代码、测试、监控都完成了，但**真实的延迟、token 用量、单次成本都还没有数据**，简历上 GenAI 那条的 `[X]% 成功率` 和 `$[X]` 暂时填不了 | 功能默认关闭；用本地假服务测了重试、超时、限流、降级、prompt 注入防护 | 提供 `OPENAI_API_KEY`（通过环境的密钥设置，不要贴在聊天里），并放行 `api.openai.com`；数据会自动出现在 `/metrics` |
| 4 | **没有部署到云上** | 没有线上可访问的 demo | `docker compose up` 一条命令在本地跑起来 | 需要一个云账号（GCP、AWS 或 Fly.io 等）。这台机器只有 4 个 vCPU，跑 Elasticsearch + PostgreSQL + API 是够的 |
| 5 | Docker Hub 偶尔限流（429）、GitHub releases 被拦 | 拉镜像要重试；k6 改为用 Go 源码编译 | 已绕过 | 不需要处理 |
| 6 | shadcn/ui 的组件仓库不可访问 | 不能用 `npx shadcn add` 命令 | 按 shadcn 同样的方式手写了组件（shadcn 本身就是把源码复制进项目） | 不需要处理 |

## B. 系统瓶颈（已修复的）

| 瓶颈 | 怎么发现的 | 根因 | 修复 | 效果 |
|---|---|---|---|---|
| ES 长时间宕机会把所有同步事件打进死信 | 跑故障演示时看日志 | "ES 整体挂了"和"某条事件有问题"用了同一套重试预算 | worker 整体暂停，不扣单条事件的重试次数（ADR 0003） | 宕机 150 秒，0 条进死信 |
| 全量 reindex 很慢 | 准备压测数据时计时 | 每篇帖子单独一次 PG 查询 + 一次 ES 请求，被往返次数卡住 | 批量读 + `_bulk` 批量写 | 134 秒 → 4.7 秒（快 28 倍），同条件 A/B 测试 |
| 新增 embedding 后原地 reindex 没有生效 | 发现 ES 里 0 篇文档有 embedding | 外部版本号拒绝了版本相同的写入（这是设计上的安全性质） | 蓝绿重建 `reindex -fresh` | 有测试覆盖"重建过程中发生的编辑不会丢" |
| 压测在 2000 req/s 时 88% 失败 | 服务端日志只看到约 3% 的失败 | 测到的是 Docker 的端口转发代理，不是服务本身 | 压测直接打容器 IP | 同样负载 0 失败 |
| 纯文字帖子被要求用 multipart 格式 | 第一次压测写请求全部失败 | API 设计缺口 | 也接受 JSON | — |
| 个性化 Feed 拖垮了搜索 | 混合负载下 1000 req/s 时崩溃 | Feed 每次请求约耗 ES 50ms CPU，ES 搜索线程池被占满（5 万次拒绝） | 召回阶段精简传输字段、关掉只贡献 1% 结果的 MLT、force merge、bulkhead 限流 | 见下文 C |

## C. 还剩下的瓶颈（诚实版）

**个性化 Feed 是整个系统里最贵的接口，单次成本比其他接口高一个数量级。**

- 在这台 4 vCPU 的机器上（ES、PG、API 和压测工具 k6 全挤在一起），Feed 流量占 5% 时，整体容量见 [benchmark.md](benchmark.md)。
- bulkhead 只能保证 Feed 过载时快速失败、不把搜索一起拖垮，**不能降低 Feed 本身的成本**。

真正的解法（按投入从小到大）：
1. **缓存每个用户的 taste 向量和候选集**，比如 1–2 分钟；点赞时让缓存失效。真实用户刷新 Feed 很频繁，命中率会很高。（这次没做，原因是压测只有 20 个用户，缓存会让数字虚高。）
2. **预计算 Feed**：活跃用户的推荐结果由后台定时算好并存起来，读的时候基本零成本。这是大公司的常见做法（fan-out-on-write 和 precompute）。
3. **向量查询和关键词搜索分开部署**：给 Feed 单独的 ES 副本或节点，物理上隔离。
4. **向量量化**：把 embedding 存成 `int8_hnsw`，内存和 CPU 都能降不少。

**压测环境本身的限制**：压测工具和被测系统在同一台机器上、共用 4 个核。所以这里的容量数字只能用来比较不同方案的相对好坏，不能当作生产环境的容量。要拿到能写进简历的容量数字，需要把压测机和服务分开部署（依赖卡点 #4）。
